# PRD-v2.1 进阶功能评审

评审对象：`ActionPulse 进阶功能实施规范 (PRD-v2.1)` 五个模块。
评审方式：逐条对照现有代码实现核对，不凭印象。

---

## 一、总体结论

**心理学部分我几乎全部同意**，而且有三处判断相当准确（习惯用并集同步、不做过期滚存、休眠应当是派生而非存储）。

但**工程部分有 5 处硬伤**：其中 3 处会直接导致功能不工作或静默丢数据，2 处是 PRD 依赖了**目前根本不存在的数据**。
另有 4 处语义必须由你拍板，5 处我建议按我的方式改。

## 二、我完全同意的部分（且已核对代码）

| 判断 | 为什么对 |
| :--- | :--- |
| **习惯用 G-Set（`completedDates` 并集）同步** | 并集满足交换律、结合律、幂等 —— 是**教科书级正确的 CRDT**，零冲突，不需要 LWW、不需要墓碑。这是整份 PRD 最漂亮的一笔。 |
| **跨天自然归零：`isDoneToday = completedDates.includes(today)`** | 派生而非存储，所以"零点重置"**不需要任何定时器、不需要任何状态变更**。而且它是纯函数，天然可测。 |
| **习惯不做过期滚存、不污染待办排序** | 关键洞察：`Task` 带 `due` 就会产生超期压力（紧迫度 D 档最高 1.2），而习惯的本质是"每天重来"。**两者必须是不同实体**，PRD 这点分得很清。 |
| **2 分钟破冰复用番茄钟** | 已核对 `usePomodoro`：`minutes` 变化且状态为 idle/finished 时会重置为新时长并回到 idle。**所以「时间到后无缝续杯 25 分钟」几乎是免费的**，不用新写计时器。 |
| **零新增依赖** | 可行。`domain/dates.ts` 已有本地日历日工具、`crypto.randomUUID` 已用于 id 生成 —— NLP 与日期解析都不需要外部库。 |
| **schema v2 → v3 平滑迁移** | 风险比想象中低：`parseBackup` 已接受**任何 ≤ 当前版本**的备份且字段缺失会补默认值；服务端只校验 `state.tasks` 是数组，多一个 `habits` 字段它照样存。**所以迁移基本是免费的**（但有一个前提，见硬伤 3）。 |
| **僵尸任务理论上与 `ageFactor` 冲突，实际不冲突** | `ageFactor = min(创建天数/7, 1)` 在第 7 天封顶，休眠阈值是第 14 天 —— 先"加速提醒"再"安静收走"，是个连贯的两段式设计。**而且 14 > 7 是运气好的选择**：阈值若小于 7 天，休眠会直接掐掉搁置补偿，那才真叫自相矛盾。 |

## 三、五处硬伤（不改就会出 bug）

### 硬伤 1　`sameState` 不认识新字段 → 习惯改动会被**静默丢弃**

已核对 `domain/merge.ts`：

```
export function sameState(a, b) {
  if (!sameTasks(a.tasks, b.tasks)) return false;
  if (!sameTombstones(a.tombstones, b.tombstones)) return false;
  ... 比较 stats 各字段 ...
  return JSON.stringify(a.settings) === JSON.stringify(b.settings);   // 结束
}
```

`mergeStates` 的返回值里 `changed` 完全依赖 `sameState`。**如果新加的 `habits` / `focusMinutes` 不写进 `sameState`**：

* 本地勾了一个习惯 → `mergeStates` 认为"没有任何变化" → `changed=false` → reducer **返回原引用** → **界面不会重新渲染**，用户点了没反应。
* 多端同步时对方的习惯改动也会被判为"无新信息"而丢弃。

这不会报错、不会红屏，只会"点了没反应"。**必须把 `habits`、`focusMinutes` 纳入 `sameState`**，并且要和它们的合并语义对应（并集）。

### 硬伤 2　模块四依赖「专注时长」，但这个数据**目前完全不存在**

我核对了：`usePomodoro` 是纯 UI 状态，`PomodoroTimer` 结束后除了播音效弹提示，**没有任何地方记录过一分钟专注时长**。
`Stats` 里也没有相关字段。

所以模块四要落地，必须**先新增埋点与新持久化字段**，例如 `focusMinutes: Record<dateKey, number>`。
而它一旦进入同步，就带来一个 PRD 没提的问题：**怎么合并？**

| 方案 | 问题 |
| :--- | :--- |
| 两边相加 | **不幂等** —— 同一次番茄钟被同步两次就重复计数 |
| 取最大值 | 幂等、不会重复计数；代价是两台设备同一天各专注 30 分钟只算 30 分钟 |
| `{日期: {设备: 分钟}}` 再求和 | 精确，但复杂度和 schema 都上去了 |

**我建议 v1 用「取最大值」**：宁可少算，也不能让数字虚高（战报数字虚高会直接毁掉它的可信度）。

### 硬伤 3　习惯的 `completedDates` **无上限增长**，而且"清理旧记录"会破坏 G-Set 语义

每天每个习惯一条字符串。10 个习惯 × 5 年 = 约 1.8 万条。
而现有同步是**整份状态覆盖推送**（每次改动 PUT 全量），所以这段历史会被反复上传。个人用很久都无感，但这是唯一会单调增长的维度。

更要紧的是：**G-Set 只能增不能减**。如果一侧按保留窗口裁掉老记录、另一侧还留着，并集立刻把它们加回来 —— 裁剪永远无效。

建议：要么 `-- 明确接受无上限`（简单、诚实），要么存 `最近 366 天 + totalCount`，
并接受"裁剪是尽力而为"这个事实。**不要假装裁剪能真正生效。**

### 硬伤 4　「专注时长」之外，模块四的复制按钮在**手机上会静默失效**

`navigator.clipboard` 要求**安全上下文**。我在上一轮实测过：手机通过 `http://192.168.1.42:5273` 访问时 `isSecureContext === false`。
所以战报的"一键复制 Markdown"在手机上**按了没反应、也不报错**。

必须做降级：`navigator.clipboard` 不可用时，回退到临时 `<textarea>` + `document.execCommand("copy")`，
再不行就把文本展开让用户手动选。这是一行 feature-detect 的事，但不做就是个哑按钮。

### 硬伤 5　模块五会让 `pendingTasks` 需要 `now`，牵动一大片调用点

已核对调用链：`pendingTasks(state)` 目前只吃 `state`，被 `sortedByUrgency` / `manualOrdered` / `quadrantBuckets` / `focusTask` 使用，
向外又被 `useActionPulse` 的 `ordered`、`pending` 使用，再向外是 `TaskList` / `QuadrantBoard` / `IdleStage`。

"14 天没动过"是**相对当前时间**的派生条件，所以 `pendingTasks` 必须变成 `pendingTasks(state, now)`，
一路改下去会碰到 6 个文件、十几处调用和若干现有测试。**这不是难点，是工作量，必须提前计入。**

## 四、需要你澄清的语义（4 处）

### 澄清 1　习惯要不要计入「今日能量槽」？

PRD 说"点击同样触发…今日能量槽充能"。但现有能量槽的分母是**「截止日在今天或更早的未归档任务 ∪ 今天完成的任务」**，
而且我当初刻意排除了"今天新建的无截止任务"，理由是**新建任务不该拉低能量槽**。

习惯加进来有两条路：

| 方案 | 结果 |
| :--- | :--- |
| **A：习惯算作今日承诺，进入同一个槽** | 语义上说得通（每日习惯**按定义**就是今天该做的）。但**必须同步修改现有能量槽测试**，且"新增一个习惯"会暂时拉低今天的百分比 |
| **B：习惯单独一个达成率环** | 任务能量槽语义不变，模块四要的"习惯达成率"本来也单独展示 |

**我倾向 A**，因为"每日习惯按定义今天到期"和现有"截止日 ≤ 今天"完全同构，是**概念一致**而不是妥协。但这条会改动现有行为与测试，需要你确认。

### 澄清 2　自然语言标记与现有三个下拉框，谁说了算？

QuickAdd 现有三个下拉（重要度 / 截止 / 预估）是 `useState` 且**跨次保留**（刻意设计）。
如果标题里又写了 `!high 今天 ~15m`：

* **标记优先**（我建议）：下拉作为缺省值，标记覆盖它；本次不修改下拉的记忆值。
* 但**必须有可见反馈**，否则用户不知道到底应用了哪个。

我建议加一条实时预览：输入时在下方显示解析结果胶囊（`高优 · 今天 · 15 分钟`）。
这样解析是**可见、可验证**的，而不是"猜它有没有生效"。这一点 PRD 没写，但缺了体验会很糊。

### 澄清 3　估算耗时的语法是**开放区间**还是**固定枚举**？

PRD 举了 `~5m / ~15m / ~30m / ~1h`。如果是固定枚举，用户写 `~45m` 会**解析失败但静默留在标题里**，变成"标题里混着 `~45m`"这种脏数据。

我建议**开放区间** `~\d+[mh]`，转成分钟并夹到合理范围（如 1 ~ 600），不在枚举里也能正确工作。

### 澄清 4　习惯要不要排序字段？

`DailyHabit` 里没有 `createdAt` / `rank`，但"横向药丸胶囊"是个**有序列表** —— 顺序从哪来？

我建议加 `createdAt: number`（顺便给休眠/统计复用），按创建时间排序即可，不引入拖拽。

## 五、我不同意 / 建议改的（5 处）

### 建议 1　「周一~周日」**绝不能解析成过去的日期**

这是我认为**最危险**的一条。如果今天是周三、用户写"周一"：

* 解析成本周已过的那周一 → 任务**立刻变成"已超期"** → `D` 拿到最高档 1.2 → **紧迫度直接冲到榜首**。
* 结果：用户用自然语言省事，却被系统惩罚了一次。

**规则应当是：一律解析为"下一个该星期几"，包含今天。** 周三写"周一"就是下周一（+5 天），永远不产生超期。
这条必须写进单测。

### 建议 2　模块四**不要自动弹模态框**

PRD 说"当今日任务与每日习惯全清…触发"。但那一刻用户刚打完勾，已经有水晶音、礼花、`celebrateAllClear()` 的全屏礼花和一条提示语。
再叠一个全屏模态弹层，一是过载，二是**如果用户马上又要记下一件事，会被挡住**。

我建议：清空时只弹一张**非阻塞**的战报卡片（桌面放在右侧台面 / 手机做成可滑出的条），
标题写"今日战报已生成 · 查看"，用户想看再点。或者至少"每天只自动弹一次"。

### 建议 3　模块一在手机上的**面板空间**会有问题

面板顶部现在已经排了：脉冲线 → 标题行 → 视图/模式切换 → 今日能量槽 → 快速输入（含三个下拉）。
再加一行习惯胶囊 + 一个骰子按钮，**手机上第一个任务卡片会被推到接近半屏以下**。

我建议：

* 习惯默认**收成一行**（`⚡ 日常 2/5`），点一下才展开胶囊；
* 骰子按钮**并进标题行**（和聚焦按钮同一排），而不是新占一行。

### 建议 4　"全部完成时自动收拢"要**留一点缓冲**

如果用户刚点完最后一个习惯，那一行**立刻收起来**，会有"我点的东西消失了"的失落感。
建议延迟约 1.5 秒再收，且收起来之后仍保留一条 `全部完成 5/5 ✓` 的紧凑提示。

### 建议 5　模块五的"一键唤醒"最好给三个选项

单纯唤醒 = 把 `updatedAt` 推到当下，让它离开休眠区。但如果用户不处理它，14 天后**它会再次休眠** —— 等于原地打转。
建议唤醒时给三个动作：**唤醒 / 给它定个截止日 / 直接删掉**。僵尸任务真正的解法是"给个日子 or 砍掉"，而不是叫醒它继续躺着。

### 补充：🎲 盲盒的随机应当**按紧迫度加权**

从 Top 3 均匀随机，等于把第 1 名的胜率压到 33%，**让算分算法白算**。
建议在 Top 3 内按 `urgencyScore` 加权抽取：既保留了"随机性打破纠结"的心理作用，算法的影响力也还在。
（这条如果你更想要"绝对随机"的仪式感，我也可以接受，但它是个**刻意的取舍**，不该默认。）

## 七、建议的依赖顺序

```
模块三 NLP ──┐（完全独立，可先做，收益最高、风险最低）
            │
模块一 习惯 ─┼─→ 模块四 战报（依赖习惯 + 专注时长埋点）
            │
模块二 盲盒/破冰（依赖聚焦模式支持指定任务）
            │
模块五 休眠（独立，但会牵动 selector 签名，放最后避免返工）
```

我建议的顺序：**三 → 一 → 二 → 五 → 四**。
理由：NLP 独立且立刻降低录入摩擦；习惯是模块四的前置；休眠动的面最大，放在稳定之后；战报是收口，且依赖最多。
