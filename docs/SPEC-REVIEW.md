## 一、总体结论

**产品与交互层面：完整，可以直接开工。** 痛点分析（执行力差 / 选择瘫痪 / 缺乏正反馈）、

**工程层面：不完整。** 规范是一份优秀的 **PRD**，但不是一份可直接执行的 **技术规范**。

## 二、P0：三处必须由需求方决策的缺口

### P0-1　"多端使用"与"纯 localStorage"互相矛盾 ⚠️ 最重要

规范同时要求：

* §6.2「完全基于客户端 localStorage 自动持久化存储」；
* §6.3「配置 --host 0.0.0.0，手机连同一 Wi-Fi 直接访问即可使用」。

但 **localStorage 按「来源 + 设备」隔离**。手机通过局域网 IP 打开页面时，拿到的是
**手机自己的** localStorage，与电脑上那份互不可见。也就是说：
**两端能各自使用，但数据永远不同步。**

这是规范里唯一的**真实产品级缺陷**，不是实现细节。

### 第二轮决策：本地优先 + 局域网同步服务

**关键认识：这不是"几十行的文件存储"，而是一个同步引擎。** 四件事缺一不可：

| 问题 | 如果不管会怎样 | 解法 |
| :--- | :--- | :--- |
| 删除会复活 | A 删掉任务，B 的旧副本下次同步把它推回来 | **墓碑（tombstone）**：删除时记录 (id → 时刻)，合并时若墓碑不早于任务本身就把任务丢掉 |
| 并发写互相覆盖 | 两台设备同时打勾，整份文件覆盖 = 一边白打 | **按任务 LWW**（`Task.updatedAt`），同分时按序列化结果做确定性兜底，保证两端**必然收敛** |
| 服务不在时不能用 | 电脑合盖，手机就打不开 | **本地优先**：手机照常读写 localStorage，恢复连接后增量同步 |
| 写完不知道对方改了 | 只能手动刷新 | **SSE 推送**：任何设备写入后广播新 rev |

**架构**：

* 后端是一个**零第三方依赖**的 `node:http` 服务（`server/`），同时托管 `dist/`、提供同步 API 和 AI 代理。
* **刻意没有把同步做成 Vite 插件**：插件的 `configureServer` 只在开发模式存在，
  生产环境跑的是静态文件，那样会变成"只有开着开发服务器才能同步"。
* 服务端**只做带版本号的存取，不实现业务 schema** —— 清洗与合并都在客户端（有单测覆盖），
  避免同一套规则两边各写一遍然后慢慢跑偏。
* **乐观锁**：PUT 带 `baseRev`，不匹配返回 409 + 最新状态，客户端先合并再重试，重试有上限。
* **合并在 reducer 里做**：拉取是异步的，用户可能在请求飞行途中又加了一条任务；
  如果把"客户端预先合并好的快照"直接覆盖上去，那条新任务就被吞掉了。
  因此同步层交回的是**服务端的原始状态**，由 reducer 在 dispatch 时刻的"当前状态"上合并。

**安全**：局域网写入是有风险的（咖啡厅 / 宿舍 / 公司网络下同 Wi-Fi 的人都能读写你的清单）。
因此**所有数据接口都要求配对 token**，服务启动时把带 token 的地址打印出来，手机打开一次即记住，
配对成功后立刻用 `history.replaceState` 把 token 从地址栏抹掉。

**明确的取舍**：

* **设置项不同步**（音量、番茄钟时长、面板常驻）。否则手机关静音会把电脑也静音。
* **可用性上限 = 那台电脑开机且没休眠**。断连时自动降级为纯本地，恢复后补齐。
* 墓碑保留 30 天，防止无限增长。

**数据迁移**：schema 从 v1 升到 v2（新增 `Task.updatedAt` 与 `AppState.tombstones`），
v1 备份会被自动迁移（`updatedAt` 取 `createdAt`），老用户数据不丢。
localStorage 的键 `actionpulse.v1` **刻意保持不变** —— 改键会把用户已有数据变成孤儿。

### P0-2　"一键 5 分钟微步拆解"在离线纯前端下无法真正实现

模块 3 要求点击后展开 3~5 个子步骤，示例是「打开文档新建空白页」这种**语义级**拆解
（参考项目 Goblin.tools 的 Magic ToDo 背后是大模型）。而 §6.1/§6.2 排除了后端与联网。

### 第二轮决策：渐进式双模

* **默认**：内置 8 组动词模板（写作 / 沟通 / 整理 / 会议 / 学习 / 编码 / 事务 / 身体），
  按标题关键词匹配，命中不了走通用兜底；用户始终可手动增删改。零配置、离线可用。
* **可选**：在设置里填 Base URL / 模型 / API Key，激活真正的语义级拆解。
* **硬约束**：`breakdownWithFallback` 保证 **AI 永远只是增强，不能成为唯一路径**。
  未配置、超时、上游报错、返回格式不可解析 —— 任何一条都静默落回模板，
  用户看到的仍然是"点一下就得到 3~5 个可执行步骤"（`src/domain/aiBreakdown.ts`，8 个单测覆盖）。

**为什么 Key 存服务端而不是浏览器**：既然同步已经需要一个本地服务，Key 就放在服务端
（`.env` 或 `data/llm.json`，只回传掩码）。这样手机零配置、Key 不过局域网、CORS 问题也顺带消失。
**两条决策在这里合流成同一个服务。**

**兼容范围**：任何 OpenAI 兼容端点都可用 —— OpenAI、
[Gemini 的 OpenAI 兼容层](https://ai.google.dev/gemini-api/docs/openai)、DeepSeek、Moonshot、
本地 Ollama / LM Studio。

**解析必须极其宽容**：模型会返回 markdown 代码块、加解释、带序号，甚至直接吐纯文本。
`parseBreakdownResponse` 依次尝试 整体 JSON / 代码块内 JSON / 第一个 `[...]` / `{steps:[]}` / 按行切分，
去重、去项目符号、截断超长项，**少于 3 条就判失败**（宁可回退，也不给用户残缺的拆解）。

### P0-3　归一化公式缺失，算法无法落地

规范写了 `Urgency = 35·I + 40·D + 15·Q + 10·A` 并要求「总分归一化为 0~100」，
但**没有给归一化公式**。按给定系数，理论最大原始分是：

```
35×1.0（高重要） + 40×1.2（已超期） + 15×1.0（≤15 分钟） + 10×1.0（搁置 ≥7 天） = 108
```

不归一化就会出现 108 分、以及"无截止时间"任务永远垫底但分值含义不明的问题。

**落地决策**：`score = clamp(round(原始分 / 108 × 100), 0, 100)`。
于是**唯一能拿 100 分的任务**就是"高重要 + 已超期 + 15 分钟内能做完 + 搁置超过一周"，
语义清晰且可解释。`src/domain/urgency.ts`

| # | 缺口 | 落地决策 | 位置 |
| :-- | :--- | :--- | :--- |
| 1 | 「今日能量槽按完成度充能」——分母是什么？ | 分母 = **截止日在今天或更早的未归档任务 ∪ 今天完成的任务**。刻意**不**把"今天新建的无截止任务"算进去，否则每记一笔待办都会把能量槽拉低，变成负反馈。 | `streak.ts: todayEnergy` |

| 4 | 未填预估耗时的任务算哪一档速赢？ | 按最慢档 0.2，避免"故意不填"来刷分。 | `urgency.ts: quickFactor` |

| 6 | 手动模式与智能模式如何共存？ | 互斥切换（顶部"智能 / 手动"）。智能模式按算分排，手动模式按拖拽位次排 + 四象限归类，卡片右侧不再显示分数（两套排序同时显示会让人更纠结）。 | `taskStore.ts: orderedTasks` |

## 四、P2：规范未提及、已补齐的工程项

1. **PWA 落地细节**：manifest（含 maskable 图标与安全区）、Service Worker
   （导航请求网络优先、带哈希的静态资源缓存优先）、iOS 的
   `apple-mobile-web-app-capable` 与 180px 触屏图标。
2. **触屏没有 HTML5 拖放**：手动模式除拖拽外补了「上移 / 下移」按钮。
3. **番茄钟**：用"目标结束时间戳"而不是 `setInterval` 累加，后台标签页被节流也不会走慢；
   结束时有音效 + 震动 + 提示。
4. **删除**：两段式确认（删除 → 确认删除），不做静默删除。
5. **音效**：音量可调、可静音；`prefers-reduced-motion` 与设置里的"关闭全部动效"都会生效；
   音效在首个用户手势时解锁（iOS 要求）。
6. **`navigator.vibrate` 在 iOS Safari 不存在**：已做能力探测，失败静默降级。
7. **健壮性**：localStorage 在隐私模式/配额超限时会抛异常，已全部 try/catch 降级到内存，
   坏数据回退到默认状态而不是白屏。
8. **测试**：规范没有任何验收标准。已补 **183 个单元测试** + 三套真实浏览器 E2E
   （单端 UI 27 项、双设备同步 36 项、AI / 离线 16 项）+ 服务端 API 冒烟 40 项。
9. **构建期守卫**：`public/` 不经过打包器，因此 `npm run build` 会先用 `node --check`
   解析 `public/`、`server/`、`scripts/` 下所有脚本，避免"构建成功但运行时静默失效"。

## 六、已知限制（如实说明）

* **同步只在同一局域网内，且需要那台电脑在运行**；电脑休眠时手机自动降级为纯本地。
* **离线模板是关键词匹配，不是语义理解**：要语义级拆解必须配置 AI。
* **墓碑保留 30 天**：超过 30 天没联网同步过的设备会失去删除记录。
* **不做账号体系 / 云备份**：换设备靠"同一局域网同步"或导出 JSON。
* **不做重复任务 / 日历订阅 / 提醒推送**：规范未要求，属于 YAGNI。
* **时钟偏差会影响冲突判定**：LWW 用的是各设备自己的 `Date.now()`。两端都开启系统
  "自动设置时间"时误差在几十毫秒内，实际不会感知；但某台设备时钟明显跑偏时，它的修改会总是"赢"。
  这一点**没有做防护**（例如用服务端 rev 兜底），属于已知风险。
* **手机主屏图标绑定配对时的 IP**：电脑换了网络或被 DHCP 重新分配地址后，手机上的图标会失效，
  需要用新地址重新打开一次。**建议在路由器上给电脑做 DHCP 静态绑定**。
* **未提交 git**：工作区根目录是一个混放了多个项目的个人仓库，是否把 ActionPulse
  纳入版本控制请你自行决定（`.gitignore` 已就绪，`data/` 与 `.env` 已被排除，密钥不会进版本库）。

## 七之一、iOS 真机适配（自查后补的两处硬伤）

需求方转达的第二轮反馈里，把 iOS 体验归纳为"可能有些安全区边缘留白"。我没有接受这个说法，
而是去看了实际配置 —— 发现两处**客观错误**：

| 问题 | 后果 | 修复 |
| :--- | :--- | :--- |
| `apple-touch-icon` 指向 `icon-192.png`，而专门为 iOS 生成的 180px 图标**从未被引用** | iOS 主屏图标尺寸不对；那个 180 图标是死文件 | 生成专用的 `apple-touch-icon.png`（180×180、**满幅不透明方形**，圆角交给系统），并在 `index.html` 正确引用 |
| `viewport-fit=cover` + 状态栏 `black-translucent`，但**完全没有 `env(safe-area-inset-*)` 内边距** | iPhone 上内容铺到 y=0，**面板标题、脉冲线、按钮会被灵动岛/状态栏盖住** | 定义 `--safe-top/right/bottom/left` 四个变量，面板、聚焦弹层、设置面板、提示条全部让位 |

顺带修正了 maskable 图标：之前是带透明圆角的，而 maskable 规范要求**满幅填充**（系统自己套遮罩），
透明角会被系统当成"图里有个透明角"。

**验证方式与边界**：Chromium 里 `env(safe-area-inset-*)` 恒为 0，无法真实模拟刘海。
因此我**注入** `--safe-top: 59px / --safe-bottom: 34px` 来验证机制本身：
面板高度仍等于视口高（border-box 生效）、内容整体下移 59px、提示条底边距 58px（24+34）、
设置面板不溢出、页面无滚动溢出。

**仍然未验证**：真机上的实际刘海/灵动岛观感、iOS Safari 的「添加到主屏幕」流程、
Safari 的 EventSource 行为、触屏手感。这些**必须在真机上试**，静态检查替代不了。

## 七、第二轮踩到并修掉的一个真实 bug（留痕）

**现象**：双设备 E2E 中，A 新增任务后 B 永远看不到；查服务端已经是 `rev 5`，
而 B 页面里 `fetch('/api/state')` 却返回 `rev 2` 的空快照。

**根因**：**Service Worker 把 `/api/state` 的 GET 响应也缓存了**（缓存优先策略对所有同源 GET 生效），
于是 B 每次都拿到第一次拉取的过期快照，合并结果永远"没有变化"。

**为什么之前没发现**：这个 bug 需要「Service Worker **且** 多端」同时成立才暴露 ——
单端 E2E 不依赖跨端推送；开发模式下 Service Worker 不注册（只在生产构建里注册）。
两个条件恰好都被前面的测试绕开了。

**修复**：

* `public/sw.js`：`/api/` 一律不拦截，直接放行到网络；缓存名升级到 `actionpulse-v2` 清掉被污染的旧缓存。
* 纵深防御：客户端所有 API 调用显式加 `cache: "no-store"`。
* 新增 `tests/serviceWorker.test.ts` 钉住这个前提，防止以后被"优化"掉。

### 修完之后，同一个文件又被我改坏了 —— 而且骗过了所有检查

修上面那个 bug 时，我在 `sw.js` 顶部的块注释里写了一句话，里面包含 `/api/` 这个路径，
而它前面紧挨着两个星号 —— **星号紧跟斜杠，等于块注释的结束标记**。
于是注释提前终结，剩下的半句话变成了代码，**整个 Service Worker 语法错误、根本不注册**。

它骗过了当时所有的检查：

| 检查 | 为什么没发现 |
| :--- | :--- |
| `vite build` | `public/` 目录**不经过打包器**，文件是原样拷贝进 `dist/` 的 |
| `tsc --noEmit` | 同上，TypeScript 根本不看它 |
| 单测 `serviceWorker.test.ts` | 当时只做**字符串匹配**（断言含 `startsWith("/api/")`），不是解析 —— 断言全绿 |
| 双设备同步 E2E 36/36 | **恰恰因为它没注册**：SW 没跑起来，自然也就没有缓存 `/api`，同步反而是通的 |

也就是说：我把「缓存 bug」修掉了，同时把整个 Service Worker 悄悄弄死了，而所有绿灯都没有告诉我。
只有当我真的去跑一次"SW 是否注册 / 断网能否打开"时才暴露出来。

**修复与加固**：

* 重写 `sw.js`（并只用不含歧义的措辞），`node --check` 通过。
* `tests/serviceWorker.test.ts` 从"字符串匹配"升级为**真实解析**：用 `node:vm` 的 `new Script()` 编译
  `public/` 下每个 `.js`。字符串断言给的是假信心，语法校验不会。
* 新增 `scripts/check-public.mjs` 并接入 `npm run build`：用 `node --check` 解析
  `public/`、`server/`、`scripts/` 下所有脚本（共 9 个文件），任一解析失败就让构建失败。
  **这个守卫写完的第一版，我又在块注释里写了同样的星号加斜杠组合，于是它自己也挂了** ——
  第二版改成全部用行注释，这类自伤才彻底消失。
* 补充了此前完全没测过的两条链路：**AI 拆解真实成功路径**（用本地假上游跑通）与
  **Service Worker 真实注册 + 断网可用**。

## 八、第三轮：浅色模式（白天模式）

需求方要求增加白天模式。计划阶段先做审计，再按 5 步实施（收敛令牌 → 拆主题块 → 切换与持久化 → 资产主题化 → 验证）。

### 审计纠正了我自己一个数字

第一遍 grep 只匹配了 `rgba(255,255,255` 与 `rgba(0,0,0`，得出「31 处硬编码」；按「所有颜色字面量」
重审后实际是 **50 处** —— 漏掉的是主色派生 `rgba(200,247,81,α)`（11 处）和 combo 徽章的橙色（4 处）。
**差点整类漏掉。**

### 为什么不能「反转颜色」（实测）

现有 9 个颜色令牌在白底上的对比度：主色 `#c8f751` **1.24:1**、`--tier-high` 2.04、`--tier-medium` 1.92、
`--text-dim` 2.61、`--teal` 1.48、`--tier-critical` 3.19（只够大字）。**9 个里 6 个不可用**，
所以浅色必须是一套重新设计的配色，而不是把值换一换。

### 新发现：深色主题自己就不达标

把 WCAG 对比度变成断言之后，最先失败的不是新写的浅色，而是**原本的深色主题**：

| 令牌 | 在 shell 上 | 在 panel 上 | 在卡片上 | 用途 |
| :--- | ---: | ---: | ---: | :--- |
| `--text-faint` `#5c6675` | 3.47 | 3.22 | **2.98** | 10px 小标签、底部提示、占位符 |
| `--tier-low` `#64748b` | 4.23 | 3.94 | **3.65** | 低紧迫度分数（11px） |

两者都是**文字**，AA 要求 4.5:1。这是我最初实现时就埋下的缺陷，浅色模式只是把它照了出来。

### 因此深色外观确实变了 —— 如实说明

计划里步骤 1 的验收标准是「深色逐像素零回归」，那一步**是达标的**：脚本化替换之后，
「每个令牌的深色值严格等于被它替换掉的原字面量」这项检查 **61/61 通过**。
但随后为了通过对比度断言，**我改了两个深色令牌**：

| 令牌 | 原值 | 新值 | 卡片上对比度 |
| :--- | :--- | :--- | ---: |
| `--text-faint` | `#5c6675` | `#7e8692` | 2.98 → **4.71** |
| `--tier-low` | `#64748b` | `#758398` | 3.65 → **4.71** |

取值方式：保持色相不变、向白方向插值，解出「最暗但仍 ≥ 4.7:1」的点（留余量，避免贴着 4.5 被舍入翻车）。
**这是本轮唯一的深色视觉变化**，动机是可读性，不是审美偏好。

### 架构

| 层次 | 内容 |
| :--- | :--- |
| `:root` | 只放与主题无关的**结构**：圆角、字体栈、安全区（7 个令牌） |
| `:root, :root[data-theme="dark"]` | 深色颜色，并设 `color-scheme: dark` |
| `:root[data-theme="light"]` | 浅色颜色，与深色**一一对应**，设 `color-scheme: light` |
| `src/hooks/useTheme.ts` | 解析偏好、监听系统主题变化、写 `data-theme` 与 `theme-color` |
| `index.html` 内联脚本 | 首次绘制之前定好主题，杜绝 FOUC |

设置项 `Settings.theme`（`system` / `light` / `dark`，默认 `system`）沿用「设置保持设备本地」的既有规则，
`merge.ts` 一行都不用改 —— 这条规则在第一轮就定下了，现在正好受益。

### 验证

| 项目 | 结果 |
| :--- | :--- |
| 深色零回归（令牌值 == 原字面量） | **61/61 通过** |
| WCAG 对比度单测（2 套主题 × 3 种底色） | **10/10 通过** |
| 主题端到端（切换 / 持久化 / 跟随系统 / 防闪屏 / 手机端） | **19/19 通过，无 console 异常** |
| 多端同步回归（主题改动之后） | **36/36 通过** |
| 单元测试总数 | **204 通过** |

防闪屏的验证方式值得一提：**把所有 JS 全部拦掉**再加载页面，此时 React 完全没有渲染
（`#root` 子节点数为 0），但 `data-theme` 已经是正确的 —— 这直接证明主题在首帧之前就已确定，
而不是「挂载之后再补一下」。

### 已知边界

* PWA manifest 的 `background_color` / `theme_color` 是静态的，安装后的启动闪屏不随主题变化。
* 发丝级装饰边框（`--line`）在两套主题下都低于 3:1。这是刻意的视觉选择（输入框另有底色区分，
  聚焦时边框升到满强度主色）。测试里**刻意不校验它**，并把原因写在测试注释里，而不是假装达标。
* 真机观感（iPhone 上的深浅色、系统主题切换动画）仍未在真机上验证。

## 九、第四轮：PRD-v2.1 五个进阶模块

需求方给出 PRD-v2.1 并要求先评审。评审提出 **5 处硬伤、4 处需澄清语义、5 处建议修改**，
需求方回复「都按照你的推荐来」，据此实施。

### 评审指出的 5 处硬伤，以及各自怎么解决的

| 硬伤 | 后果 | 解决 |
| :--- | :--- | :--- |
| `sameState` 不认识新字段 | 习惯改动被判成「无变化」→ reducer 返回原引用 → **界面不重渲染 + 多端静默丢弃** | 扩写 `sameState`，纳入 `habits` 与两张日指标 map，并写了「只改打勾日期也必须判为变了」的回归测试 |
| 模块四依赖的「专注时长」根本不存在 | 战报没有数据可报 | 新增 `daily.focusMinutes` 埋点；番茄钟跑动中累计、结束时结算、退出时结算零头 |
| `completedDates` 无上限增长、裁剪会破坏 G-Set | 假装能裁剪就是自欺 | 明确**接受无上限**（每天每习惯一条日期键，个人用几十年也就几万条），并在文档里写明裁剪在 G-Set 上本就不成立 |
| 战报复制按钮在手机上是哑按钮 | `navigator.clipboard` 要求安全上下文，局域网 HTTP 不满足 | `copyText()` 做能力探测，降级到 `execCommand`；再失败就提示手动选中（文本本来就展示在弹层里） |
| `pendingTasks` 需要 `now`，牵动一大片 | 休眠是相对当前时间的派生条件 | 签名加 `now`（默认 `Date.now()`，既有调用与测试不受影响），新增 `useNow()` 低频 tick 让休眠随时间自然生效，并新增 `dormantTasks` 选择器 |

### 采纳的建议

| 建议 | 落地 |
| :--- | :--- |
| `周一` 永不解析成过去 | 解析为「下一个该星期几」含今天；8 个周几名的「绝不早于今天」断言 |
| 战报不自动弹模态框 | 清空时只出现一条非阻塞提示（可关闭），弹层必须用户主动打开 |
| 习惯收成一行、骰子并进标题行 | `HabitBar` 默认折叠成 `⚡ 日常 2/5`；骰子放进标题行与聚焦按钮同排 |
| 全部完成延迟收拢 | 延迟 1.5 秒再收，避免「我点的东西消失了」 |
| 唤醒给三个出口 | 休眠行同时提供**定个日子 / 唤醒 / 删除** —— 单纯唤醒 14 天后又会休眠，等于原地打转 |
| 盲盒按紧迫度加权 | 权重取 `urgencyScore`（兜底 1），并有用例断言第一名的命中率显著高于 1/3 |
| 估时用开放区间 | `~(\d+)(m|h|分钟|小时)`，夹到 1~600 分钟 |
| 习惯加 `createdAt` | 用于药丸排序与休眠展示 |
| 主题/习惯设置不跨端同步 | 沿用既有的「设置保持设备本地」规则，`merge.ts` 未因此新增复杂度 |

### 需求方澄清的两项（我给的默认被采纳）

* **习惯计入今日能量槽**：理由是「每日习惯**按定义**就是今天到期」，与现有「截止日 ≤ 今天」同构。
  这会改动既有能量槽测试，已同步更新并补了习惯参与的用例。
* **`focusMinutes` 多端合并取最大值**：幂等、不会因为同一份数据同步两次而重复计数；
  宁可少算也不让战报数字虚高（虚高会直接毁掉战报的可信度）。

### 验证

| 项目 | 结果 |
| :--- | :--- |
| 单元测试 | **304 通过**（新增 NLP 28、习惯 20、盲盒 12、休眠 11、战报 10，以及 store/merge 的连带用例） |
| 类型检查 / 构建 | 均通过 |
| v2.1 功能端到端 | 14/15 通过（唯一失败是我的选择器写错，已单独补验） |
| 2 分钟 → 续杯 | **用假时钟快进 125 秒真正跑通**：到点出现续杯入口 → 续杯后进入 25 分钟并开始跑 → 专注时长已记录 |
| 习惯 G-Set 并集 | **4/4 通过**：A 在 10-01 打勾、B 在 10-02 打勾（时间戳更新），合并后两端与服务端都是 `[10-01, 10-02]`；第三台全新设备看到完整并集 |
| 多端同步回归 | **36/36 通过** |
| 主题回归 | **19/19 通过** |

顺带一个测试方法上的教训：习惯并集第一次跑是「两端一致但不是并集」。
原因是**我在页面仍连着同步时直接改 localStorage**，随后被应用的自动保存覆盖了 —— 是测试写法的竞态，不是应用缺陷。
改成「用 init script 在应用启动前种好状态、且两端先后同步」之后 4/4 通过。
**遇到「两端一致」这种通过时尤其要警惕**：一致不等于正确，两边可能一起错到同一个值上。

### 数据兼容

schema 升到 **v3**（新增 `habits` 与 `daily`）。v1 / v2 备份仍可导入：`parseBackup` 接受任何不高于当前版本的备份，
缺字段由清洗函数补默认值。服务端只校验 `tasks` 是数组，多出来的字段照存，因此**不需要服务端改动**。

### E2E 阶段挖出的两个真实缺陷

| 缺陷 | 怎么发现的 | 修复 |
| :--- | :--- | :--- |
| `GET /api/health` 仍上报 `schema: 2` | 新写 E2E 时顺手断言了版本号一致 | 服务端抽出 `SCHEMA_VERSION` 常量并注明与 `BACKUP_VERSION` 联动 |
| **Escape 关不掉战报弹层** | E2E 断言「Esc 可关闭战报」失败 | App 的 Escape 处理漏了 `setDebriefOpen(false)` —— 加弹层时忘了接进去 |

第二个是真缺陷不是测试问题：设置面板与聚焦模式都能用 Esc 关，唯独新加的战报不能，属于一致性漏洞。
这也是为什么每个新弹层都该有一条「Esc 能关掉它」的断言 —— 加弹层时最容易漏的就是全局快捷键这类**跨组件的隐性契约**。

> 附注：E2E 里偶尔出现 `409 (Conflict)` 的 console 报错，那是乐观锁的正常工作路径
> （客户端拿到 409 → 合并服务端状态 → 重试）。浏览器会把非 2xx 响应记为 console error，无法从 JS 抑制，也不影响功能。
